## 2. 프레임 한 장의 여정

| 단계 | 주체 | 하는 일 | 목표 시간(CPU) |
|---|---|---|---|
| 0 | 폰 | `getUserMedia` → canvas 960px 리사이즈 → JPEG(q=0.7) → WS 바이너리 전송 | — |
| 1 | C1 | 세션 확인, 처리 중 프레임이 `MAX_INFLIGHT` 이상이면 **즉시 드롭** | <1 ms |
| 2 | C1→C2 | 디코드, 리사이즈, (선택) ROI 원근 보정, 다시 JPEG | ~10 ms |
| 3 | C1→nginx→C3 | 과자 마스크 + 형상 특징 계산 (fast: OpenCV / precise: SAM 2) | fast ~15 ms · precise ~1 s |
| 4 | C1→C4 | seq 순서 검사, 추적, 검사선 통과 시 카운트, 결과 오버레이 그리기 | ~10 ms |
| 5 | C1 | 대시보드 WS로 결과 JPEG + 카운트 푸시, 폰에 통계 전송 | — |

## 3. 핵심 설계 결정

### D1. C1이 오케스트레이터 (체인 전달 방식이 아님)
C1이 C2 → C3 → C4를 차례로 호출하고 응답을 받습니다(PDF의 "C4 → C1 역전송"은 C4의 HTTP 응답이 맡습니다).
- 장점: 각 서비스가 **요청 하나 → 응답 하나인 순수 함수**가 되어 혼자 테스트하기 쉽고, 타임아웃·드롭·지연 측정을 한 곳에서 처리합니다.
- 각 서비스는 다른 서비스 주소를 몰라도 됩니다. C1만 압니다.

### D2. 백프레셔(Backpressure)는 C1 한 곳에서
- 폰은 목표 fps(기본 10)로 보내되 `ws.bufferedAmount`가 크면 건너뜁니다.
- C1은 처리 중인 프레임 수가 `MAX_INFLIGHT`(기본 = C3 복제본 수 + 1)를 넘으면 새 프레임을 **버립니다**. 큐에 쌓지 않습니다. 실시간 시스템에서는 늦게 처리된 프레임은 가치가 없습니다.

### D3. C3는 무상태, C4는 상태 보유
- C3는 프레임 한 장만 보고 판단하므로 **복제(scale-out)** 할 수 있습니다.
- 추적과 카운트는 프레임 간 연속성이 필요하므로 C4 **단일 인스턴스**에서 합니다.
- 복제본 때문에 응답이 순서 없이 도착할 수 있으므로 C4가 `seq`로 정렬 여부를 판단합니다 ([05-detection.md](05-detection.md#4-추적과-카운트)).

### D4. GPU 없음 → 하이브리드 추론
- **fast (매 프레임)**: OpenCV 임계값과 컨투어. 위치 추적과 1차 판정에 씁니다.
- **precise (필요할 때만)**: SAM 2.1 hiera-tiny에 box prompt를 넣습니다. 인코더 1회로 프레임 안 모든 과자의 정밀 마스크를 얻습니다.
- **SAM 2를 언제 돌릴지는 C4가 정합니다.** 판정이 애매한 트랙(특징값이 임계값 근처이거나 fast 투표가 갈림)에 `needs_precise=true`를 붙이면, C1이 precise 슬롯이 비어 있을 때 다음 프레임을 precise로도 보냅니다. 명백한 정상·불량에는 CPU를 쓰지 않습니다.
- 비교 실험용으로 `precise_policy=interval`(주기적으로)과 `off`도 지원합니다.
- 참고: 이 시뮬레이터는 배경이 단순해서 OpenCV만으로도 정확도가 높을 가능성이 큽니다. SAM 2는 **조명·노이즈 조건에서의 견고성**과 발표 내용 구현을 위한 것이므로, 막히더라도 데모는 성립합니다.

### D5. 공개 경로는 cloudflared Quick Tunnel
- 폰 카메라는 HTTPS에서만 동작합니다. Quick Tunnel이 무료로 HTTPS를 제공합니다.
- 공유기·방화벽·Wi-Fi 기기 간 차단 문제를 모두 우회합니다.
- C3 로드밸런서 포트(`:8090`)와 각 서비스 포트는 **터널에 노출하지 않습니다**.

### D6. 계약은 코드로 고정
- [`shared/schemas.py`](../shared/schemas.py)(pydantic)를 모든 Python 서비스가 import합니다.
- JS(폰, 대시보드)는 [03-messages.md](03-messages.md)의 JSON 예시를 따릅니다.
- 계약을 바꿀 때는 **두 사람 모두 리뷰**한 뒤 문서와 코드를 함께 수정합니다.

## 5. 촬영 환경 배치

```
 [모니터 1: 시뮬레이터 /sim/]  ←── 폰 (삼각대/거치대, 화면과 평행)
 [모니터 2 또는 팀원 노트북: 대시보드 /]
```
- 시뮬레이터와 대시보드는 같은 서버에서 제공되므로 아무 기기에서나 열 수 있습니다.
- 정답 비교: 시뮬레이터 상단의 정상/불량 카운트와 대시보드 카운트를 나란히 놓고 비교합니다.

### 촬영 규칙 (라인 3개를 한 화면에 담을 때)
| 규칙 | 이유 |
|---|---|
| 폰을 **가로**로 들고, 시뮬레이터 **캔버스 전체(라인 3개)** 가 화면에 들어오게 합니다 | 캔버스는 대략 1300×450으로 가로로 깁니다 |
| 전송 해상도는 **960px** | 640px로 보내면 과자 지름이 약 35px까지 작아져 원형도가 흔들립니다 |
| 대시보드에서 **ROI 4점을 캔버스 네 모서리에** 찍습니다 | 원근 보정을 하고 캔버스 바깥(제어 패널 등)을 잘라냅니다. 검사선 0.34가 시뮬레이터와 일치하려면 필수입니다 |
| 검사선 `line_x = 0.34` | 시뮬레이터가 세는 위치(`SCAN=0.34`)와 같아서 두 카운트가 거의 동시에 올라갑니다 |
| 시뮬레이터 **"정답 외곽선 표시"는 끕니다** | 정답 윤곽선이 찍히면 판정이 오염됩니다 |
| 빨간 검사선 점선과 "LINE 0x" 글자는 그대로 둬도 됩니다 | 가늘고 작아서 크기 필터로 걸러집니다. 다만 빨강이 갈색과 색상이 가까우니 C3 색 범위를 잡을 때 확인합니다 |
